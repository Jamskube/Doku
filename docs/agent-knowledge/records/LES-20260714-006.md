## Situation
Workarounds — portée `tauri`. Entrée d'origine datée du 2026-07-14.

## Rule
Tuer l'arbre d'un sidecar de façon fiable (Windows)

## Evidence
: un process sidecar qui en spawne d'autres (ex. `ollama.exe` → `llama-server.exe` en grand-enfant) laisse ses descendants **orphelins** si on kill juste le parent (`CommandChild::kill`, et même `taskkill /F /T` ne survit pas à un crash de l'app). Solution robuste : un **Job Object Windows** — `CreateJobObjectW` + `SetInformationJobObject(JobObjectExtendedLimitInformation, LimitFlags=JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)` + `AssignProcessToJobObject(job, OpenProcess(PROCESS_SET_QUOTA|PROCESS_TERMINATE, pid))`. Le noyau termine **tout l'arbre** dès la fermeture du dernier handle du job = à la mort du process (fermeture propre OU crash) ; les enfants créés APRÈS l'assignation héritent du job. Garder le handle du job en vie tout le process (le fermer tue l'arbre) ; `TerminateJobObject` pour un stop explicite (le job reste réutilisable). Supérieur au pidfile+sweep : nettoyage garanti noyau, pas de fenêtre orphelin, pas de hasard de réutilisation de PID. Le `HANDLE` (raw ptr) n'est ni Send ni Sync → newtype + `unsafe impl Send+Sync` pour le stocker dans le State Tauri. Crate `windows` 0.61 (features `Win32_System_JobObjects`/`_Threading`/`Foundation`/`Security`)
