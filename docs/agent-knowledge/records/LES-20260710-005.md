Gotchas — portée `verification`. Entrée d'origine datée du 2026-07-10.

## Rule
`/impeccable critique` (dual-agent, contexte neuf) rattrape des bugs que l'auto-vérification manque — utile après une story dont on a soi-même écrit la vérif

## Evidence
_Aucune preuve détaillée dans l’entrée d’origine._

**Fusionné** (Trois formulations de « critic (plan) + code-reviewer (diff) = deux filets complémentaires ».) :
- [2026-07-10] Sur une feature **data/destructive**, enchaîner `critic` (sur le **plan**, contexte neuf, avant code) **puis** `code-reviewer` (sur le **diff**, après) rattrape deux classes de défauts distinctes : le critic cadre les risques d'architecture (ex. scope de suppression trop large), le reviewer trouve les défauts d'implémentation (ex. `meta.json` non atomique / non réconcilié)
- [2026-07-24] **Critic (plan) + code-reviewer (diff) = deux filets complémentaires, pas redondants.** Au S13 (Epic 15 RAG), le reviewer a rattrapé sur chaque story de code des défauts que le critic — pourtant approbateur sur le plan — ne pouvait pas voir : un plan correct peut être mal implémenté. Exemples réels attrapés avant le natif : garde `buildIfMissing:false` qui testait l'EXISTENCE du meta au lieu de sa VALIDITÉ (modèle+version) → ré-embed intégral silencieux du dossier derrière une question ; deux prédicats censés être « le même » (badge d'UI vs branche de décision) qui divergeaient quand le réglage est vide → régression d'honnêteté. Le critic raisonne sur les intentions, le reviewer sur le code réel. Garder les DEUX passes sur toute story > 100 LOC ou surface données/persistance.
