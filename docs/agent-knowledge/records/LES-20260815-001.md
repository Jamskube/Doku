## Situation
Gotchas — portée `pdf`. Entrée d'origine datée du 2026-08-15.

## Rule
PDF.js TRANSFÈRE le tableau passé en `data` à son worker : le buffer de l'appelant est DÉTACHÉ

## Evidence
(`byteLength` tombe à 0, `buffer.byteLength` aussi) dès `getDocument()`. Aucune erreur, aucun avertissement — le tableau devient simplement vide. Vécu sur « Organiser les pages » (ADR-0022) : les octets du document étaient chargés par pdf.js pour les vignettes PUIS conservés pour écrire la copie ; à l'enregistrement, pdf-lib recevait 0 octet et rendait « Un des documents n'a pas pu être ouvert ». **Invisible en test unitaire** (aucun test Node ne peut importer `pdf.ts`, qui tire le worker via la syntaxe `?worker` de Vite) — trouvé uniquement au banc navigateur, en cliquant réellement sur Enregistrer. Correctif posé **dans `loadPdf`** (`data: bytes.slice()`) plutôt que chez l'appelant : le piège est désamorcé pour tout futur appelant, au prix d'une copie. Règle générale : toute API qui accepte un `TypedArray` et travaille dans un worker est suspecte de transfert — vérifier `byteLength` après l'appel avant de réutiliser le tableau.

**Fusionné** (Même piège de tampon détaché ; l’entrée MuPDF renvoyait déjà explicitement à celle de PDF.js.) :
- [2026-08-15] **MuPDF (WASM) détache les tampons DEUX fois, dans les deux sens** — même famille que le piège pdf.js ci-dessus, mais sans worker, donc encore plus discret. (1) **En entrée** : `Document.openDocument(bytes, …)` détache `bytes` ; l'appelant qui relit son propre tableau ensuite lit 0 octet. Parade : `openDocument(bytes.slice(), …)` à CHAQUE point d'entrée (`pdf-edit-text.ts` en a trois). (2) **En sortie, le piège vicieux** : `saveToBuffer('').asUint8Array()` ne rend pas des octets à soi mais une **VUE sur le tas WASM de MuPDF** ; toute allocation ultérieure (ouvrir une autre page, relire le document pour vérifier) fait croître ce tas et **DÉTACHE la vue déjà rendue** — le tableau qu'on croyait tenir devient vide plus tard, loin de l'appel fautif. Parade : copier HORS du tas immédiatement, `new Uint8Array(doc.saveToBuffer('').asUint8Array())`, sur la même ligne. Corollaire pour tout WASM : une vue mémoire rendue par une bibliothèque n'est valide que jusqu'à son prochain `malloc` — la copie n'est pas une précaution, c'est la seule façon correcte de sortir des octets.
